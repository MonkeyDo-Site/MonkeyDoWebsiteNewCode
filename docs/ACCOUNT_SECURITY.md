# Owner/staff account security increment

Local implementation only. No Droplet resize, deployment, paid-service activation, DNS change, provider credential installation or external email occurred. Email tests use Django's in-memory mailbox; that is not verified external delivery.

## Owner verification and recovery

- Owner password verification creates a pre-authentication challenge, not a privileged session. Staff accounts sign in without MFA.
- Six-digit email codes expire in ten minutes and allow five attempts per challenge. Resends wait at least one minute, supersede the prior code and do not reset attempts/expiry. Per-owner sending and verification limits add temporary throttling without permanently disabling the account.
- Verification consumes a code atomically, authenticates the owner and creates a 30-day remembered-browser token. Only its keyed digest is stored; the browser cookie is HttpOnly/SameSite and Secure in staging.
- The original verification expires after 30 days even if the owner repeatedly signs in on day 29. Login does not slide or extend that deadline. Active sessions are also checked at expiry.
- Owner-designated secondary email supports MFA-code delivery and password-reset requests. Visitors cannot supply an arbitrary recovery destination. Changing recovery settings revokes other owner sessions/remembered browsers while retaining the current verified session.
- Ten offline recovery codes can be generated by the verified owner. They replace email MFA, not the password; each works once. Raw codes are displayed only in the no-store generation response, never saved in session, database, audit or URL. Digests and actual use/retirement facts are stored. Replacing a set retires previously unused codes without falsely recording their use.
- Failed owner-email delivery leaves the owner unauthenticated, exposes a truthful recovery message and creates a persistent Dashboard security alert. Secondary email or an offline code remains available. Provider exceptions/message contents are not persisted.
- Staff cannot change owner recovery settings, generate owner codes or promote themselves to owner. Database constraints allow only one owner identity.

## Password resets

Reset requests use generic responses for eligible/nonexistent addresses, with network and per-email request limits. Only active staff accounts with usable passwords qualify. Owner reset requests may use the configured secondary address; the token remains bound to the real account without changing its primary address.

Reset links expire after one hour and become invalid after use, credential changes or account security-version changes. A reset does not log anyone in automatically or bypass owner MFA. Password validation enforces the approved minimum ten characters and Django's standard similarity/common-password checks.

Reset email templates and all actual sending remain test-mode/in-memory. Resend sender verification, delivery, bounce/failure/retry reporting and real owner delivery tests remain prerequisites to hosted owner acceptance. Do not use a console backend, print codes or add a staff recovery bypass to work around missing delivery.

## Staff management and sessions

Verified owner screens create/edit staff usernames, emails, passwords, enabled status and currently implemented capability grants. No password or password hash is displayed. New passwords are not forcibly changed at first login. The staff screen cannot edit/demote the owner or grant owner/security-management permissions.

- Usernames are permanent, case-insensitively unique and retained when an account is disabled. Application checks and database guards prevent renaming/reuse. Related security records protect identities from deletion.
- Credential, enabled/staff/owner status, group membership and permission changes invalidate previous sessions and remembered browsers through a version checked on every authenticated request. Direct and reverse permission/group updates are covered. Current requests already in flight are not a promise of retroactive cancellation.
- Staff saves reject stale versions, validate permissions server-side, audit metadata and record only a password-changed boolean. Concurrent case-variant username creation produces one success and a controlled validation rejection.
- Twelve hours without activity logs out; active use refreshes inactivity. Owner verification still expires at its independent 30-day limit.
- Sign out all sessions revokes that account's sessions and remembered browsers. Shared staging access remains a separate control.
- The Django identity/group inspector is read-only, shares the protected login endpoint and hides password hashes. Operational identities are managed through the custom owner screens.

The capability picker currently covers implemented customer/comment/history and read-only booking permissions. The full booking/payment/program/export/backup permission matrix will expand alongside those features; those operations are not silently enabled here.

## Shared staging password

`APP_ENV=staging` protects page previews with an owner-managed shared password, separate from staff login and owner MFA. Passwords are hashed. A valid shared password issues a signed HttpOnly access ticket for one day; changing the password invalidates old tickets immediately. The password expires after 90 days until the owner replaces it.

A shared ticket permits public-page testing, not entry to staff/customer/owner areas. Authentication/reset/verification endpoints remain accessible for sign-in and recovery. A verified owner can access only the staging-password setup screen without a ticket, allowing recovery from an unset/expired gate without bypassing owner MFA. The settings inspector excludes the shared password hash.

The review-only nginx example now delegates the shared gate to the application. A second independently managed nginx password would not rotate with the owner settings, so it is not configured in that example. No example has been installed or activated.

## Bootstrap and boundaries

After approved hosting setup, install migrations first, then interactively create the single owner with `python manage.py createsuperuser`, supplying the owner's chosen username, primary email and strong password privately. Existing local identities are backfilled with security metadata without changing their IDs, passwords or roles. If old data contains conflicting owner identities or case-colliding usernames, migration fails rather than silently renaming/deleting anyone; resolve only with owner review.

Connect and verify real staging email before expecting browser-accessible owner MFA/reset delivery. Once the owner can verify, configure the secondary email, save offline codes privately and set the shared staging password in Owner → Staging access. Never paste credentials, recovery codes or email tokens into chat/PR comments or training recordings.

## Verification

All **130 repository tests pass on PostgreSQL 17**. The suite checks MFA expiry/replay/attempt limits, recovery-code rotation/use, secondary delivery, reset expiry/reuse, delivery failure, secure-cookie flags, CSRF, staff grants/revocation, identity guards, inactivity and the independent staging gate. PostgreSQL tests also race the same MFA code, a recovery code across two challenges, case-variant staff creation, and simultaneous redemption of the same password-reset link. Reset completion rechecks the token under a user-row lock and records a credential-free audit fact.

A separate local Chromium walkthrough used a disposable test database and in-memory email to complete owner MFA, update recovery email, create staff, set staging access and open the preview as a separate visitor. Private staff pages still required sign-in. Screens passed at 1440px and 390px without horizontal overflow or browser errors. No raw codes/passwords were recorded in screenshots. This localhost test is not evidence of deployed TLS/provider delivery.
